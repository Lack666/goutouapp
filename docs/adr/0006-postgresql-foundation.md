# ADR 0006: PostgreSQL foundation and ownership boundaries

Status: accepted for Phase 2B (2026-09-27).

Version selection was checked against the official release records for
[SQLAlchemy](https://pypi.org/project/SQLAlchemy/),
[Alembic](https://pypi.org/project/alembic/),
[psycopg](https://pypi.org/project/psycopg/) and
[PostgreSQL](https://www.postgresql.org/support/versioning/). Exact Python
packages are resolved in the root `uv.lock`; Compose pins PostgreSQL 18.6.

## Decision

- Use one root uv lockfile with SQLAlchemy 2.1, psycopg 3, Alembic and PostgreSQL
  18 for the development service. The FastAPI app constructs a database holder
  without opening a connection; `/ready` is the database probe and `/health`
  remains process liveness.
- Every table has a UUID primary key generated by Python before insert. Public
  identifiers do not reveal row counts. `created_at` and `updated_at` are
  PostgreSQL `TIMESTAMPTZ`; `now()` supplies insert defaults and SQLAlchemy
  supplies `updated_at` on ORM updates. The application connection sets UTC.
  Direct SQL writers must set `updated_at` themselves.
- `Person`, `Relationship`, `Conversation` and `AgentRun` carry a non-null
  `user_id`. A `Message` belongs through a non-null `conversation_id`.
  Composite foreign keys on relationship/person, conversation/relationship and
  run/conversation prevent linking records owned by different users, even if a
  caller bypasses the repository. Repository reads take `user_id` explicitly.
  This is a structural boundary, not authentication.
- `Conversation.relationship_id` is nullable because a general AI conversation
  may have no named person or relationship. If supplied, the composite foreign
  key requires the same owner.
- User deletion is restricted while owned records exist. Person deletion is
  restricted while relationships exist. Relationship deletion is restricted
  while conversations reference it. Conversation deletion cascades its messages,
  but is restricted while AgentRun records reference it. These choices avoid
  accidental deletion of user data and run history; a later explicit privacy
  deletion flow must order and audit removals.
- Schema changes use Alembic migrations only. Tests create a randomly named
  database inside a separately configured `_test` namespace, migrate it, use
  rollback per test, and drop it after the run. A separate acceptance script
  exercises CLI upgrade/downgrade/upgrade on another disposable database.

## Consequences

The current repository/service functions are enough to validate persistence
and ownership, without exposing CRUD endpoints or implementing auth. Test DB
provisioning needs a PostgreSQL role allowed to create/drop databases, as the
Compose development role is. Production migrations should use a separately
authorized deployment role.
